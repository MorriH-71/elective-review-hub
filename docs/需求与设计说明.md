# 需求与设计说明（v2.0）

## 1. 业务背景与痛点

教务部门每学期开设多门选修课，报名数据由不同渠道汇总成 Excel 表。原先的做法是所有记录一律进审核队列，由教务人员逐行核对，实际暴露出两个问题：

- **大量记录根本不需要人看**：字段漏填、手机号格式错误、重复提交，这些申请人自己就能修正，却占用了审核队列，也把「待审核」指标灌得很大；
- **真正需要判断的问题反而缺少依据**：课程时间是否撞车、学生是否曾修过并通过同一门课，这些要结合课表和成绩记录才能判断，旧系统只给一个布尔状态，无法解释「为什么被拦」。

v2.0 的核心改动，是把一条预检流水线重构成**申请受理关口 + 审核队列 + 系统自动决策**三层，并让自动决策可复核、可改判。

## 2. 从使用者反馈中得到的需求

| 反馈 | 设计响应 |
|---|---|
| 规则全通过的申请应由系统自动通过 | 新增系统策略 A01：审核阶段无风险命中时直接 `approved`，`decision_source=system` |
| 系统通过之后，管理员可自行选择是否复核、修改结果 | 新增「人工复核」区：确认无误 / 改判驳回 / 改判待补正，强制意见、改来源、全量留痕 |
| 联系方式格式这类硬错误应在申请阶段就驳回 | R01/R02/R03（及 R07）从审核阶段前移到申请受理关口，命中只写驳回台账，不写 `enrollments` |
| 建议拦截应该是「时间冲突」「已通过课程重复选修」这类需要人工判断的情况 | 新增 `student_schedule`、`course_history` 两张参考表与 R05 / R06 两条风险规则，输出带证据的「建议拦截」 |

## 3. 范围界定

**本期做**

- 报名表 Excel / CSV 导入、模拟申请提交、字段标准化
- 申请受理关口 4 条硬校验与驳回台账、驳回清单导出
- 审核阶段 2 条风险规则（+1 条可选容量提示）及可解释的判定依据
- 无风险自动通过策略、管理员人工复核与改判
- 审核工作台：筛选（含审批来源）、分页、全选、批量审核、批量复核
- 详情：全部申请字段、风险提示与证据、学生课表与历史修读、审核轨迹
- 6 状态状态机、三角色权限、操作日志、通过名单与模板导出
- 课程上课时间维护、规则按阶段分组配置

**本期不做**

- 真实邮件 / 短信发送（只生成名单）
- 统一身份认证（用请求头切换演示角色）
- 交互看板、问卷分析、成绩与考勤统计
- 生产部署与真实个人信息

看板所需的统计 SQL 与 `/api/stats` 已预留，接上是下一迭代的事。

## 4. 两阶段流程

```
                    ┌── 不通过 ──→ application_rejections（驳回台账，不进审核系统）
申请人提交 / 导入 ──┤
                    └── 通过 ──→ run_review_rules()
                                    ├─ 命中 R05 / R06（R04 可选）→ pending，人工审核队列
                                    └─ 无命中 + A01 开启 → approved，decision_source=system
                                                              ↓
                                          管理员复核：confirm（打标）/ override（改判）
```

- **申请受理关口（`run_gate`）**：R01 必填、R02 联系方式格式、R03 重复报名、R07 课程代码与截止时间。命中即返回 `accepted=false` 与逐条原因；导入场景下只把原始行、命中的规则编码与原因写入 `application_rejections`。
- **审核阶段（`run_review_rules`）**：R05 上课时间冲突、R06 已通过课程重复选修、R04 容量提示（默认关闭）。命中 R05/R06 → `blocked`（建议拦截）；仅 R04 → `warning`；无命中 → `pass`。**审核阶段规则永不自动改状态**。
- **系统策略（A01）**：仅当 `level=pass` 时自动通过。这是全系统唯一自动改写状态的规则，结果带来源标记、带轨迹、可关闭、可复核、可改判。
- **人工复核（`apply_recheck`）**：仅管理员、仅 `decision_source=system` 且 `status in (approved, notified)`。`confirm` 只打 `human_rechecked=1`；`reject` / `supplement` 改状态 + 改来源为 `manual` + 强制意见 + 写 `override` 日志。

## 5. 规则设计

| 编码 | 阶段 | 名称 | 判定逻辑 | 输出 |
|---|---|---|---|---|
| R01 | intake | 必填字段完整 | 学号、姓名、学院、手机号、邮箱、课程代码任一为空 | 拒绝受理，列出缺失字段名 |
| R02 | intake | 联系方式格式 | 手机号须匹配 `^1[3-9][0-9]{9}$`；邮箱须含 `@` 与域名 | 拒绝受理，指出具体字段与值 |
| R03 | intake | 重复报名检测 | 同一学号 + 同一课程，与库内记录或本批次记录比对 | 拒绝受理，说明重复来源 |
| R07 | intake | 课程代码与报名时效 | 课程不存在 / 未开放 / 提交时间晚于截止日 | 拒绝受理，说明原因 |
| R05 | review | 上课时间冲突 | 申请课程与 `student_schedule` 中同日且节次区间重叠（闭区间相交） | 建议拦截，附冲突课程与节次 |
| R06 | review | 已通过课程重复选修 | `course_history` 中存在同课程 `passed=1` 记录 | 建议拦截，附学期与成绩；`passed=0` 不命中并注明允许重修 |
| R04 | review | 课程容量提示 | 已通过人数 + 本批次累计 ≥ 容量 | 需留意（默认关闭） |
| A01 | system | 无风险自动通过 | `run_review_rules().level == 'pass'` | 系统自动通过；关闭后全部 `pending` |

- 规则配置存 `rule_config`，`stage` 区分阶段，`enabled` 控制开关，`params` 存参数，改规则不改代码。
- 每条受理记录保存 `precheck_result`（JSON：命中编码、名称、阶段、说明、`evidence` 判定依据、检查时间），详情页逐条展示。
- 时间冲突判定：`class_day` 相同且 `a.start <= b.end && b.start <= a.end`，节次为闭区间。

## 6. 状态机

| 状态 | 说明 | 允许动作 |
|---|---|---|
| pending 待审核 | 命中风险规则，等待人工判断 | 通过、驳回、要求补正、取消 |
| supplement 待补正 | 资料不全或复核改判后的待补正 | 通过、驳回、补正后重新提交、取消 |
| approved 已通过 | 系统自动通过或人工通过 | 标记已通知、取消；系统来源可复核改判 |
| notified 已通知 | 已进入通知名单 | 系统来源可复核改判 |
| rejected 已驳回 | 人工驳回或复核改判 | 终态 |
| cancelled 已取消 | 报名取消 | 终态 |

`ALLOWED_TRANSITIONS` 集中定义常规转移，非法转移动作返回 409。**复核改判是受控的逆向操作**，不走常规转移表，而由 `apply_recheck` 单独校验来源、状态、权限与意见必填，日志用 `override` 明确标注，避免「已通过 → 已驳回」被误当成普通审核。

## 7. 数据模型

| 表 | 作用 | 主要字段 |
|---|---|---|
| `courses` | 课程、容量与上课时间 | course_code、capacity、deadline、class_day、start_period、end_period、class_time |
| `applicants` | 报名人 | student_id、name、college、major、grade、phone、email |
| `enrollments` | 报名记录（审核系统核心） | status、precheck_level/result、decision_source、human_rechecked、rechecked_by/at、reviewed_by/at/comment |
| `student_schedule` | 学生本学期已选课表 | student_id、course_name、class_day、start_period、end_period |
| `course_history` | 历史修读记录 | student_id、course_code、semester、score、passed |
| `application_rejections` | 申请阶段驳回台账 | student_id、source、reasons、raw_data、created_at |
| `rule_config` | 规则配置 | code、stage、level、enabled、params、description |
| `reviewers` | 演示账号 | username、role |
| `operation_logs` | 操作日志 | enrollment_id、action、from_status、to_status、operator、comment |
| `app_meta` | 演示数据版本 | key、value |

视图：`v_pending_review`（人工审核队列）、`v_auto_approved`（待复核清单）、`v_review_stats`（课程维度汇总）。
索引：状态、课程代码、学号、审批来源、课表学号、历史学号+课程、日志关联与时间字段。

`sql/schema.sql` 建表，`_migrate()` 为旧库补齐新列，`sql/views.sql` 在迁移之后重建视图与依赖新列的索引，`sql/seed.sql` 用 `ON CONFLICT DO UPDATE` 更新主数据但**不覆盖管理员改过的规则开关**。

## 8. 事务与一致性

- 单条审核 / 复核：`UPDATE enrollments` 与 `INSERT operation_logs` 在同一 `get_conn()` 事务中，异常整体回滚。
- 批量审核 / 批量复核：逐条调用同一函数，任一条状态不合法、来源不符或记录不存在，整个批次回滚。
- 申请受理：逐行写入并实时维护本批次去重集合与课程累计数；硬校验不通过的行只写台账，不影响其余行。
- 演示数据版本（`app_meta.demo_version`）变化时自动重建，且升级时把规则开关重置为推荐默认。

## 9. 界面设计要点

- **模拟提交申请**：以申请人身份填表，提交瞬间给出「未受理 + 逐条原因」或「已受理 + 系统自动通过 / 转人工」结论，内置合规、格式错误、重复报名三个示例按钮。
- **申请受理页**：展示最近一次导入/提交的分类去向，以及申请阶段驳回台账（可导出清单）。
- **先详情后决定**：列表操作是「查看并审核」，弹窗依次展示全部申请字段、风险提示与证据、学生课表与历史修读、审核轨迹，最下方才是决定区。
- **复核区**：仅系统自动通过且当前身份为管理员时显示「确认复核无误 / 改判为驳回 / 改判为待补正」。
- **全选与批量**：表头全选支持半选、跨页保留已选快照；批量确认自动排除不适用记录；批量复核仅管理员可用。
- **规则配置按阶段分组**，并说明每组规则对流程的影响。

## 10. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 后端 | Python 3.10+ / FastAPI | 轻量、自带接口文档、类型校验 |
| 数据库 | SQLite + 原生 SQL | 零配置，SQL 能力可见 |
| 数据处理 | pandas + openpyxl | 表格清洗与多 sheet 报表；缺失时自动回退标准库 |
| 前端 | 原生 HTML / CSS / JS | 无构建、无外部 CDN，离线可用 |
| 测试 | pytest | 规则、状态机、事务、导入导出 |

演示模式与正式模式共用 `static/app.js`：前者用内置数据模拟接口，后者通过 `fetch` 调真实 API，保证预览页与运行版本行为一致。
